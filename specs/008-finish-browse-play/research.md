# Research: Finish Browse and Play (008)

Sources: Stash's GraphQL schema pinned in `crates/stash-core/graphql/stash-v0.31.1.graphql`; the
Stash web UI source (local checkout at `/home/bbulder/stash-source/stash`, `latest_develop`, read
for behaviour only; everything is checked against the pinned v0.31.1 schema); the
semantic-tagging plugin's README; and what 006–007 built.

## R1. Query budget per user action (the core of this plan)

- **Decision**: every user action has a fixed, written budget of GraphQL operations, each with a
  named operation and a listed selection set ([contracts/query-budget.md](contracts/query-budget.md)).
  The budgets for this feature:

  | Action | Operations (max) |
  |---|---|
  | Show a page of Scenes (any search, filter, sort, size) | 1 `ScenesPage` (cards + count) |
  | Open a scene page | 0 for the title, cover, and Play (from the card); then 1 `SceneDetails` |
  | Open "All files" on the scene page | 1 `SceneFiles` |
  | Open galleries on the scene page | 1 `SceneGalleries` |
  | Rest on a performer / tag / studio chip | 1 `PerformerCard` / `TagCard` / `StudioCard`, once per item per session (cached) |
  | Open a filter picker (performers, tags, studios, groups, galleries) | 0 when cached; otherwise 1 `ChoiceList<Kind>` per server until the cache refreshes (the Tags picker: ordinary tags plus `SemanticVocabulary`, at most 2) |
  | Semantic vocabulary and tag colours (Tags picker or first scene page) | 0 when cached; otherwise 1 `SemanticVocabulary` per server (R12) |
  | Save tag colours (Settings → Tag colours) | 1 `SaveTagColours`, plus 1 `SemanticVocabulary` when the set of rule fields changes |
  | Open the saved filters menu | 0 when cached; otherwise 1 `SavedSceneFilters` |
  | Open a new Scenes tab (default filter) | 0 when cached; otherwise 1 `UiConfig` (default filters, play settings) per session |
  | Play history | 1 `SaveActivity` per checkpoint (once a minute while playing) and at the end; 1 `AddPlay` per viewing |
  | Seek-bar thumbnails | 2 plain GETs per scene (the VTT and the sprite sheet), on first hover, cached |
  | Hover preview | 1 plain GET (the animated preview), on first hover, cached |

- **Rationale**: the user asked for strictly scoped queries; the constitution (Principle IV)
  forbids N+1 patterns and requires each new operation's request count and payload to be reviewed
  in the plan. Writing budgets down per action makes them testable.
- **Alternatives**: one "everything" scene query (rejected: over-fetches galleries, every file,
  rich performer data); per-section queries (rejected in clarification Q1: more round trips).

## R2. Enforcing the budget (performance QA)

- **Decision**: three layers, all automated:
  1. **Selection snapshots** (stash-core tests): every operation's GraphQL text is generated by
     Cynic and compared with a checked-in golden file
     (`crates/stash-core/graphql/operations/<Name>.graphql`). Adding a field fails the test until
     the golden file (and so the review diff) shows it. A second test forbids heavy fields in the
     card and chip tiers (for example `paths.stream`, `files` beyond the primary file's facts,
     `performers.image_path` in card queries, any `scene_markers` in card queries).
  2. **Request recording**: `StashClient` gets an optional recorder that sees every operation's
     name, request and response byte counts, and duration (the one chokepoint is
     `StashClient::graphql`, plus the plain GETs). Core tests against a mock server assert exact
     counts per action ("opening a scene page: 1 request, operation `SceneDetails`"); native
     transition tests assert the effects per action (one `LoadSceneDetails`, no per-chip loads
     until a hover rests).
  3. **Live audit** (perf-harness, read-only, Testing): the bench turns on the recorder and
     reports per-scenario rows: requests, response bytes, and server time for showing a page (50
     and 1000), applying a filter, opening a scene page, opening each extra section, resting on a
     chip, opening each picker (cold and cached), and a 10-minute simulated viewing's writes. Each
     row has a budget from R1; the report fails if a count is exceeded.
- **Rationale**: snapshot tests catch over-fetching at review time; counting catches N+1 at test
  time; the live audit catches payload growth on real data.
- **Alternatives**: manual review only (rejected: regressions creep in); server-side logging
  (rejected: needs Stash changes).

## R3. Filters: a typed criterion model, sent as Stash's filter input

- **Decision**: the core gets a typed model of every scene criterion
  (`stash-core/src/scenes/filter/`): one variant per criterion of v0.31.1's `SceneFilterType`
  (title, code, path, folder, details, director, oshash, checksum, phash, duplicated, organized,
  rating, o_counter, resolution, orientation, framerate, bitrate, video/audio codec, duration,
  resume_time, play_duration, play_count, last_played_at, has_markers, is_missing, tags, tag_count,
  performer_tags, performers, performer_count, performer_age, performer_favorite, studios, groups,
  galleries, url, stash_id, stash_id_count, interactive, captions, interactive_speed, file_count,
  date, production_date, created_at, updated_at, custom_fields), each with the modifiers the web
  UI offers for it. It converts to Cynic input objects for `SceneFilterType` (typed and checked
  against the schema at build time, like 007's queries), so a page query is still one request.
- **Saved filters** store Stash's *saved* criterion format (`object_filter`, written by the web
  UI's `applyToSavedCriterion`, which differs from the query input: multi-value criteria carry
  `{items: [{id, label}], excluded, depth}`), plus `find_filter` (sort, per page, query) and
  `ui_options` (display mode). The core decodes that format into the model; keys it doesn't know
  are collected and reported (FR-005) instead of silently dropped. Labels saved with items let a
  restored filter show its chips without a lookup.
- **Default filter**: `findDefaultFilter` is deprecated in v0.31.1 ("default filter now stored in
  UI config"); the default lives in the server's UI configuration (`configuration { ui }`, key
  `defaultFilters`, by mode). One `UiConfig` read per session (cached) gives it, along with the
  play settings (R6).
- **Semantic-tagging placeholders** (FR-003b): the model has a `Semantic` group of criterion kinds
  (Trait, Trait Category, Label, Role, Role Category, Pluggable, Action + variation,
  Mise-en-scène/Location, Timeline relation, Archetype, Look) that the menu shows as described but
  disabled, and that are never sent to Stash. A tab or saved filter carrying one keeps it and
  shows it as "not yet available" (Phase 4 fills them in from the plugin's `custom_fields` data).
- **Alternatives**: raw JSON variables built by hand (rejected: loses the schema check that
  caught real mistakes in 007); filtering locally (rejected by the spec: Stash applies filters).

## R4. Choice lists for pickers

- **Decision**: one `ChoiceList<Kind>` query per kind (performers, tags, studios, groups,
  galleries) with `per_page: -1` and the narrowest selection: `id`, `name`, and aliases where the
  type has them (performers `alias_list`; tags and studios `aliases`, a list; groups `aliases`, one
  string split on commas; galleries use `title`). No images, no counts. Tags are split (spec
  FR-003c): `ChoiceListTags` holds ordinary tags only (every semantic flag and `variantOfTagId`
  `IS_NULL`), and semantic tags come from `SemanticVocabulary` (R12). The
  list is cached per server under `choices:<kind>` and refreshed quietly on the cache's schedule
  (003's refresher), so opening a picker is instant and costs Stash nothing after the first time.
  The drop-down filters the cached list locally as letters are typed (names and aliases,
  case-insensitive, accent-folded). Performer images in visible rows come through the image cache
  (one GET per visible row, cached), never in the list query.
- **Rationale**: matches the web UI's full drop-downs (clarification Q3) while keeping the load
  on Stash to one lean list fetch per server per refresh.
- **Payload check**: a 20,000-name list at about 40 bytes per entry is under 1 MB once; the audit
  (R2) records the real size on Production (read-only) and Testing.

## R5. Scene page: two tiers plus lazy extras

- **Decision**: the card already holds title, cover, duration, resolution, studio, and date, so
  the page renders those and Play with no request. `SceneDetails` then selects only what the page
  shows by default: details, code, director, date, rating, organized, play count, resume time,
  play duration, URLs, studio (id, name), performers (id, name, image path for the chip image),
  tags (id, name), groups (id, name, scene index), markers (id, title, seconds, end seconds,
  primary tag name), the primary file's facts (as 007), and `paths` (`screenshot`, `webp`, `vtt`,
  `sprite`). `SceneFiles` (every file's facts and path) and `SceneGalleries` (id, title, image
  count) load when their sections open.
- **Chip details** (`PerformerCard`: age/birthdate, gender, country, scene count, favourite;
  `TagCard`: description, scene count; `StudioCard`: parent studio, scene count) load after the
  pointer or focus rests 400 ms, once per item per session, cached.
- **Performer chip images** are image GETs through the thumbnail service (resized small), cached
  like scene thumbnails; the page request carries only the image path.

## R6. Play history, matching the web UI's rules

- **Decision** (from the web UI's `track-activity.ts`):
  - `sceneSaveActivity(id, resume_time, playDuration)` takes the play duration **since the last
    save** (Stash adds it up); sent at each checkpoint (once a minute of actual playing,
    clarification Q4) and when the viewing ends.
  - `sceneAddPlay(id)` once per viewing, when the share watched (playing time ÷ duration) reaches
    the server's `minimumPlayPercent` (UI configuration; the web UI's default is **0**, meaning the
    first save counts the play). This replaces the spec's guessed 20%.
  - A resume point at **98% or more** of the duration is saved as 0 (cleared). This replaces the
    spec's guessed 5%.
  - The web UI's own `trackActivity` setting is read but not used: the viewer's "Save play
    history" switch decides (clarification carried over from 005).
- **Reliability**: unsaved writes go into a small per-profile queue on disk
  (`play-history.json` in the app's data folder), flushed in order when the connection returns or
  at the next session for that server; quitting or switching servers flushes first with a short
  deadline, then leaves the rest queued (SC-006).
- **Cache patch** (Principle IV): after a successful save, the cached `scene:details:<id>` entry is
  patched (resume time, play count, play duration) rather than invalidated.

## R7. Resume and chapters in the player

- **Decision**: opening a scene with a resume point (and "Resume where you left off" on) starts
  mpv at that time (`start` option on load) and shows a "Start from the beginning" control for a
  8 seconds; markers become chapters drawn on the seek bar from `SceneDetails` (no extra
  request), with next/previous chapter keys added to the keymap's player level (PageUp/PageDown,
  following mpv's convention, listed in help).

## R8. Animated previews without a video pipeline

- **Decision**: the hover preview is Stash's animated WebP (`paths.webp`), fetched with the API
  key on first hover, kept in the disk cache, and decoded off the UI thread with the `image`
  crate already in the build (WebP animation support) into frames at the card's size, then shown
  as a sequence of image handles on a timer while hovered. Only one preview plays at a time
  (clarification Q5); its frames are dropped when the pointer leaves. A preview starts after the
  pointer or focus rests on a card for **200 ms** (clarification), shorter than the 400 ms chip
  rest because the preview costs nothing once cached and the fetch is one GET.
- **Constitution**: Principle V allows moving previews as image formats (animated WebP) and
  forbids the UI decoding video; an animated image decoded to frames is an image format.
- **Memory**: frames at card size (~256×144 RGBA ≈ 150 KB) × frame count (Stash's previews are
  about 9 short segments; typically 50–150 frames) ≈ 7–22 MB for the one playing preview.

## R9. Seek-bar thumbnails

- **Decision**: Stash's sprite sheet (`paths.sprite`, one JPEG) and its WebVTT index
  (`paths.vtt`, cues `start --> end` with `sprite.jpg#xywh=x,y,w,h`) are fetched on the first
  seek-bar hover (2 GETs), cached, and the hovered time's region drawn by cropping the sheet's
  image handle (iced's image `crop`).

## R10. The transcoding fallback

- **Decision**: when mpv reports it can't decode a file (an open error, not a network error), the
  player's error offers "Play transcoded". Choosing it opens Stash's MP4 transcode
  (`/scene/<id>/stream.mp4`, built by the core from the profile's base URL, the API key in a
  header like the direct stream) with an explicit `transcoded` flag on the open request. The
  player's direct-stream guard (002 R6) allows a non-direct URL only with that flag; the player
  shows a "Transcoded" badge, and the log records the scene and mpv's reason. A transcode that
  also fails shows both reasons and stops.

## R11. Saved per-tab state

- **Decision**: the Scenes screen's saved fields gain the search text, the criteria (the typed
  model, serde), the applied saved filter's id (for display), and the wall mode; the session file
  version goes from 1 to 2 (007's rule: no migrations, a version change starts fresh with Home).
  Criteria are saved in the viewer's own form, not Stash's, so a tab restores without a request.

## R12. Semantic vocabulary and tag colour rules

- **Decision**: one `SemanticVocabulary` request per server (cached as `semantic:vocabulary`,
  refreshed with the tag choice list) with one aliased `findTags` per semantic flag (`NOT_NULL`)
  and one for common variants (`variantOfTagId NOT_NULL`), each selecting `id name aliases
  custom_fields`, plus one alias per extra colour rule selecting `id custom_fields`.
  `custom_fields` is a map in Stash's schema (no per-key selection), so it is selected only in
  this request, whose result is bounded by the plugin's vocabulary and the flagged tags, never on
  the 20,000-tag ordinary list or on scene queries. Chips look types and colours up by tag id in
  this cache, so `SceneDetails` keeps `tags{id name}`.
- **Colours belong to flags, not tags** (clarification, [contracts/tag-colour.md](contracts/tag-colour.md)):
  an ordered list of rules (flag → `#rrggbb`) with defaults for the seven semantic types, kept in
  Stash's UI configuration under `semanticStashViewer.tagColours`. Every tag with a flag shares
  its rule's colour. Finding a rule's tags is one `NOT_NULL` filter evaluated by Stash, so the
  viewer never reads every tag to find colours, and changing a colour is one small write
  (`configureUISetting`, which replaces just that key) instead of a write per tag.
- **Reading cost**: none extra. The rules arrive in the `UiConfig` request the viewer already
  makes; the tags they match arrive in the vocabulary request.
- **Plugin parity**: the plugin's `loadTagCategoryMaps` (`src/ui/page-and-registration.js`) runs
  the same per-flag aliased query to colour by type, with fixed `TAG_CATEGORY_COLORS`; the
  default rules follow its priority order. The plugin can read the same UI-configuration key to
  share the colours. A scrubbed fixture of the real vocabulary result (Production, read-only)
  checks the parsing.
- **Alternatives**: a colour custom field on every tag (rejected by the user: finding coloured
  tags means scanning, and updating means a write per tag); a distinct derived colour per
  semantic tag (rejected as too complicated for little gain, since type colours carry the
  meaning); colours in a local settings file (rejected: not shared across machines or with the
  plugin, and Principle I keeps library data in Stash); `custom_fields` on `SceneDetails` tags
  (rejected: semantic tags carry large JSON fields, multiplied per scene page).
